Root cause

Both flaws have the same shape: PHP frees a request's memory while internal bookkeeping still points into it, and the next request on that worker reads the freed memory as if it were live.

PHP allocates memory for each request and releases it when the request ends. If the request dies unexpectedly — a fatal error, or an allocation that hits memory_limit — the cleanup path can run with half-built or already-freed data. The worker process survives. Its globals still reference memory that no longer exists. The next request handled by that worker can consume the stale state, which an attacker can steer into controlled memory corruption or into a leak of live process memory.

The two CVEs are two different points where this can happen:

  • CVE-2026-109618 — RCE via OOM corruption. An out-of-memory failure interrupts PHP while request data is only partly initialised. Request cleanup then treats the invalid data as valid.
  • CVE-2026-109619 — RCE via stale global state. A fatal error leaves request-owned internal state pointing at memory that was freed when the request ended. A later request on the same worker uses that stale state before normal initialisation resets it.

Which SAPI you run decides how easy the second step is. On Apache with mod_php, a fatal error during request startup still runs request cleanup and the worker is reused, so the stale state is reachable on the next request. On PHP-FPM, a failure during startup terminates the worker instead, so the path that matters is a fatal error after startup succeeded — reached through the Session upload-progress feature, which is enabled by default.

Impact

Unauthenticated remote code execution, and a separate path to reading live process memory. The bug is in the PHP engine, not in your application code.

Exploitation does not need an account, a session, or a flaw in the CMS on top. A "Hello World" page on an affected PHP version is enough. The researchers demonstrated pre-authentication remote code execution against WordPress, Drupal, Joomla, MediaWiki, Roundcube, Magento, phpMyAdmin, Nextcloud, Laravel, Symfony and WHMCS, and against plain PHP scripts.

Separately, they showed that an attacker can read live worker memory without achieving code execution at all. PHP parses multipart requests before normal initialisation finishes, so an attacker can make freed heap contents get URL-encoded into an oversized or malformed PHPSESSID response cookie. That memory can hold passwords, session tokens, API keys and certificates belonging to other users' requests or to the server itself.

Risk is highest on Apache with mod_php, where an unauthenticated request can trigger the attack before any application code runs. Every SAPI that serves web requests is in scope: PHP-FPM, mod_php, php-cgi, FrankenPHP and LiteSpeed.

Which versions are affected

Every PHP version from 5.4 onwards is affected by at least one of the two flaws. Patches exist for the four supported branches.

PHP 8.1 and older no longer receive updates from the PHP project. Some distributions and LTS vendors provide backported fixes — check yours. The PHP security team also published minimal source backports for the 7.4, 8.0 and 8.1 branches, for people building from source or without an LTS vendor.

Linux distributions and LTS vendors received the patches before the public release, so the update is usually a normal package upgrade. The volunteer rpms.remirepo.net repository was not updated: move to distribution packages or build from source. PHP 8.2 reaches end of life on 31 December 2026 and takes no further security fixes after that, so plan the upgrade to a supported branch.

Do this now

Updating is the only complete fix. Everything else buys time or adds defence in depth.

If you own a website and do not run the server

  1. Ask whoever hosts it whether the PHP security update is applied. The fix must land on PHP itself. Updating WordPress, a theme or a plugin does not fix it.
  2. If the answer is no, or the answer takes more than a day, ask for the site to be taken offline until it can be patched. Several public bodies did exactly this.
  3. Watch for security messages from services you use, and treat any "change your password" request that arrives with the publicity around this incident with suspicion. Phishing campaigns ride on headlines like this one.

If you run servers

  1. Inventory every PHP installation, internet-facing first. PHP is often bundled inside appliances and vendor images, and prevalence is not directly observable from the application layer. Do not limit discovery to outdated versions: all versions may be affected.
  2. Update to the fixed release for your branch — 8.5.12, 8.4.27, 8.3.36 or 8.2.35.
  3. Restart every PHP worker after the update, so the fix is actually live in every process.
  4. Preserve logs and configuration snapshots before you change anything, then look for evidence of compromise: web shells, new cron entries, new accounts, PHP workers launching shells or downloading tools.
  5. Restrict internet access to PHP systems that could not be patched in time.
  6. Keep WAF rules as defence in depth. Cloudflare shipped managed rules for both CVEs to all customers including the free tier, several hours before disclosure. A WAF reduces exposure; it does not replace the patch.

If you are a hosting or platform provider

  1. Ship the patched packages to every customer image and let them upgrade, and tell them clearly which versions are fixed.
  2. Offer a documented mitigation path for customers who cannot upgrade immediately, and be explicit about what it does and does not stop.
  3. Publish an inventory of affected products so downstream operators can find what they are running.

Interim mitigations

These reduce exposure to specific attack paths. They do not make an installation safe, and PHP says updating is the only complete solution.

For CVE-2026-109618, RCE via OOM corruption

  • Set memory_limit=-1, in a way applications cannot override, such as php_admin_value in the FPM pool or the Apache configuration. Check that no pool, directory or application setting puts a finite limit back. This removes the controllable memory-limit failure, but an underlying allocation failure can still reach the vulnerable path.
  • Set a low post_max_size — 8M for applications that do not need uploads, 32M when uploads are required. Keep upload_max_filesize below it. Enforce limits for decoded request size, field count, multipart part count, header count and nesting depth at the web server or proxy, including for requests without a usable Content-Length.
  • Use a container or cgroup limit as an availability boundary, with a policy that kills only the affected worker. Do not substitute RLIMIT_AS or RLIMIT_DATA: they can trigger the vulnerable allocation failure.

For CVE-2026-109619, RCE via stale global state

  • Set session.upload_progress.enabled=0 and restart every worker. Apply it in php.ini, the FPM pool or server configuration, so it applies before request parsing. Do not rely on ini_set() or a per-directory .user.ini. This blocks the confirmed session paths, not other variants.
  • On PHP 8.5, set fatal_error_backtraces=0 and restart every worker. This blocks the confirmed fatal backtrace path only.
  • Remove invalid or deprecated per-request settings that emit diagnostics before initialisation. Hiding diagnostics with error_reporting, display_errors or @ does not help.
  • Fix attacker-reachable fatal errors and execution timeouts, including failures in callbacks, upload or import processing and cleanup.

Worked example

; php.ini — FPM pool or server level, not .user.ini session.upload_progress.enabled = 0 post_max_size = 8M upload_max_filesize = 2M memory_limit = -1 ; PHP 8.5 only fatal_error_backtraces = 0 ; then: restart every worker

What to hunt for

These bugs execute below the application layer, so application logs may show very little context. Look one level lower.

  • Unusual multipart requests followed by memory-limit errors or repeated HTTP 500 responses.
  • Unexpectedly large or malformed PHPSESSID response cookies — a normal session id is short, and this one is a leak of heap contents.
  • Unexplained PHP worker churn: workers restarting or dying under load without a matching traffic explanation.
  • PHP worker processes launching shells or downloading tools.
  • New web shells, unexpected cron jobs, and newly created accounts tied to PHP processes.

National agencies also ask operators to look for backdoors an attacker may have installed, and to treat vendor advisories about appliances and services that bundle PHP as part of the same patch wave.
